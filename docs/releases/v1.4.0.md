# v1.4.0

The MRCM validator now enforces **in-group cardinality**, the last rule it loaded
and ignored. Fixing it surfaced a second defect in a check that has been shipping
since v1.0.0.

No exported signature changed. One `IssueKind` constant is added, and three shapes
of expression change verdict — in both directions, so read
[Behaviour change](#behaviour-change) before upgrading.

---

## In-group cardinality

`AttributeDomain.InGroupCardinality` was parsed, stored and exposed, and nothing
read it. The specification defines it as

> "The number of times the given attribute can be assigned a distinct
> (non-redundant) value within a **single relationship group**"

against `attributeCardinality`, which counts

> "...within the definition of each concept or expression"

They constrain different things, and an expression can satisfy one while breaking
the other. Three finding sites spread over three groups are fine under a concept
cardinality of `0..*` **and** an in-group cardinality of `0..1`; the same three in
one group break only the second. So the check is independent and reports its own
kind:

```go
mrcm.IssueKindInGroupCardinalityViolation // "in_group_cardinality_violation"
```

Two things it deliberately does not do:

- **The ungrouped attribute set is not a relationship group.** This is the same
  reading the ECL evaluator applies to group 0 of `PropertiesByGroup`. Counting it
  would let `a = x, a = y` outside braces break an in-group maximum that says
  nothing about ungrouped attributes. Being ungrouped when the rule requires a
  group is still reported, as `ungrouped_violation`.
- **A rule with `Grouped: false` is skipped**, because its attribute does not live
  in relationship groups at all.

## The second defect: occurrences vs distinct values

Both cardinality fields are defined over a *"distinct (non-redundant) value"*. The
concept-level check counted **occurrences**, so

```
22298006 : { 363698007 = 74281007 } { 363698007 = 74281007 }
```

— the same finding site asserted twice — counted as two and broke a cardinality of
`0..1`. It asserts nothing a single statement does not, and a normalizer would
collapse it. Both checks now count distinct values.

"Non-redundant" goes further than distinct: two values where one subsumes the other
are redundant too. That is **not** implemented, on purpose. Collapsing them needs
subsumption testing against the terminology, which would turn a counting step into
one that fails when the provider is unavailable — and it can only ever lower a
count, so the effect of leaving it out is a violation reported that a fully
normalizing implementation would not report, never the reverse. Normalize before
validating if you need it.

## An ambiguity, and the choice made

The specification says how many times an attribute **"can be"** assigned a value in
a group. That settles the maximum. It does not say whether a **minimum** applies to
every group of the concept or only to groups where the attribute appears, and the
readings differ sharply: under "every group", an in-group cardinality of `1..1` on
one attribute makes any group without that attribute a violation.

This enforces the minimum **only within groups that contain the attribute**. The
reason is asymmetry of harm — under that reading a real constraint may go
unreported; under the other, a finding with a site group and a separate "due to"
group is accused of breaking a rule about an attribute it never put there. This
package has already had to remove one accusation of exactly that shape, where a
bare precoordinated concept was flagged for a missing mandatory attribute.

Stated plainly so nobody discovers it by surprise: **`1..1` behaves like `0..1`
here**, and a minimum above 1 means "a group that uses this attribute needs at
least that many distinct values". If you have MRCM content that depends on the
other reading, that is a bug report worth making. It is a decision under an
ambiguity, not a conclusion, and
`TestValidate_InGroupCardinality_MinimumAppliesWhereTheAttributeIs` is the one
place to change if it is revisited.

## `"inGroupCardinality": "0..0"` is a no-op

The zero value of `Cardinality` is `{Min: 0, Max: 0}`, which read literally forbids
the attribute inside any group. Enforcing that would make every `AttributeDomain`
built as a Go literal *without* the field reject its own attribute — a silent break
for any caller that constructs a `Model` rather than loading JSON, where an absent
field already becomes `0..*`.

So `{0, 0}` is treated as unset. Nothing is lost: "never inside a group" is what
`Grouped: false` already says, and it is already reported as a
`grouped_violation`. A JSON model spelling out `"0..0"` should set
`"grouped": false` instead.

## Behaviour change

Three shapes change verdict, and not all in the same direction:

| Expression | Before | After |
|---|---|---|
| Two distinct values of one attribute in one group, against `inGroupCardinality: "0..1"` | valid | `in_group_cardinality_violation` |
| The same value asserted twice, against `cardinality: "0..1"` | `cardinality_violation` | valid |
| The same value asserted twice, against `cardinality: "2..*"` | valid | `cardinality_violation` |

The last row is the one to watch, because it is the distinct-value fix pointing the
other way: a MINIMUM that was being satisfied by repetition is no longer. Two
copies of one value were counted as two occurrences and met a minimum of 2; they
are one distinct value and do not. That is the same sentence of the specification
producing a stricter verdict rather than a looser one, and it is correct — but if
your content repeats values to satisfy a minimum, it will start failing.

If you validate authored content, expect the first row to surface real findings:
that rule was never enforced at all. Any snapshot test over `Result.Issues` will
move.

## Upgrading

1. `go get -u github.com/gofhir/ecl`.
2. If your `Model` is built in Go rather than loaded from JSON, nothing breaks: an
   unset `InGroupCardinality` constrains nothing. Set it where you want the rule
   enforced.
3. If you loaded MRCM JSON, the field was already being parsed and is now applied.
   Check `in_group_cardinality_violation` in your results before assuming a
   regression.
