# v1.3.0

One subject: `Parse` was slow enough to be a denial-of-service vector, and nothing
in the repository would have told you.

No exported signature changed. Two constants are added, and input past them is now
rejected — see [Behaviour change](#behaviour-change) if you generate ECL
programmatically.

---

## The problem

`Parse` uses an ANTLR-generated parser with the default ALL(\*) adaptive
prediction. On this grammar that is quadratic. Measured on an M-series laptop,
single-threaded:

| expression | size | v1.2.0 | v1.3.0 |
|---|---|---|---|
| 3 clauses — the size real queries are | 170 B | 31 ms | **0.09 ms** |
| 10 refinement clauses | 222 B | 114 ms | **0.20 ms** |
| 50 refinement clauses | 1.1 KB | 4.5 s | **0.59 ms** |
| 100 refinement clauses | 2.2 KB | 7.6 s | **1.08 ms** |
| 200 refinement clauses | 4.4 KB | 27.5 s | **2.07 ms** |
| 200 nested parentheses | 409 B | 12.2 s | rejected in µs |

Allocations for the 100-clause case: **92,037,707 → 18,253**.

The middle rows are the ones that matter, because they are not adversarial. `* :
a = x, a = x, …` is a plain conjunction that a person writes by hand or a query
builder emits, and at a hundred clauses it took over seven seconds. A CPU profile
put the time in `ParserATNSimulator.closureWork` and in the garbage collector
trying to keep up with it.

Why it is worse than "slow": this library is built to sit inside FHIR servers,
ValueSet authoring tools and CDS pipelines, where the expression arrives in a URL.
A parser that spends seconds on a few hundred bytes lets any caller stall a worker.

## The fixes

### Two-stage parsing

`Parse` now runs SLL prediction first, which is linear and decides every
expression this grammar expresses unambiguously. SLL can reject input that full
ALL(\*) accepts, so a failure is not an answer — it means "reparse properly", and
stage two runs the original path. Same grammar, same visitor, so the tree and the
error messages are identical either way; the fallback is paid only by input SLL
cannot decide.

Note for anyone tempted to copy this: the usual advice is to pair SLL with
`BailErrorStrategy`, and on this grammar **that does not terminate** — see below.
The speed came from the prediction mode, not from bailing.

### Bounded input

```go
const (
	MaxInputBytes   = 1 << 20 // 1 MiB
	MaxNestingDepth = 100
)
```

Checked in a linear prescan before parsing starts. That ordering is the point:
ANTLR offers no way to interrupt a parse in progress, so a `context` deadline
would let a caller stop *waiting* while the goroutine kept burning CPU — no
defense at all for a server. Bounding the input is the only thing that bounds the
work.

Nesting depth is the one axis that stayed superlinear after the prediction change,
which is why it is capped rather than fixed. At the limit a parse costs 0.5 ms.

The limit is set from data, not taste: across the 121 official SNOMED
International examples and the 136 bundled conformance cases, the deepest
expression nests **4** levels. 100 is 25× that headroom.

Brackets inside a quoted term or between the pipes of a `|term|` are data, not
structure, and are not counted — `{{ D term = "a(b" }}` is one parenthesis that
never closes, and counting it would drift the depth upward across clauses and
reject valid expressions.

### A fuzz target

`FuzzParse` asserts that no input panics, that a nil tree never comes back with a
nil error, and that no parse runs away. Its seed corpus is every official example
plus a set of deliberately awkward shapes. `make fuzz` runs it; CI runs a
60-second pass per pull request and uploads any crasher as an artifact.

It should have existed from the first commit. Its absence is why the numbers above
went unnoticed through four rounds of code review and a release.

### Benchmarks

`BenchmarkParse_RefinementClauses`, `BenchmarkParse_NestedParens` and
`BenchmarkParse_Typical`. A performance claim without a measurement is a guess,
and the README had been making one. What they guard is the *shape*: a superlinear
curve means the parser has fallen back to full LL on ordinary input.

## What the fuzzer found, twelve seconds in

```
* {{ D term = "C:\temp" }}
```

26 bytes. An invalid escape inside a term — any backslash that is not `\\` or
`\"`, so a Windows path, a regex, a typo. Under SLL prediction paired with
`BailErrorStrategy` it did not terminate: the heap passed 5 GB and kept climbing.

`BailErrorStrategy` makes `Sync` a no-op, and without resynchronization the parser
loops in a subrule without consuming input; the default strategy consumes a token
and breaks the loop. So stage one keeps the default error strategy and pays a
wasted recovery walk on invalid input, which the input limits bound anyway.

This was a regression introduced *by the fix in this release*, not a v1.2.0 bug —
v1.2.0 rejects that input cleanly in 9 ms. It never shipped. It is written up here
because the sequence is the argument for the target: a change that made the parser
7,000× faster also introduced a 26-byte kill switch, and the thing that caught it
was a test written the same afternoon rather than any amount of re-reading.

The exact input is committed under `ecl/testdata/fuzz/` and replays as an ordinary
test.

## Behaviour change

An expression over 1 MiB, or nesting deeper than 100, now returns a
`*ecl.ParseError` instead of being parsed. Both report through the existing type,
so a caller switching on it to answer 400 needs no new case.

Hand-written ECL will not notice — the deepest real expression measured is 4
levels. If you *generate* ECL and might nest deeply, check
`ecl.MaxNestingDepth` before building. If you have legitimate ECL that exceeds it,
that is a bug report worth making; the limit is a guess about the world, and the
world gets a vote.

## Upgrading

1. `go get -u github.com/gofhir/ecl`.
2. Nothing to change unless you generate deeply nested expressions.
3. If you were working around slow parsing with a cache or a timeout, measure
   again before keeping it.
