# v1.5.0

Two capabilities that close the last two filters the parser modelled and the
evaluator refused, and one fix to a member filter that was returning a wider set
than it was asked for.

No exported signature changed. **Two behaviours do change**, and both move results
rather than break the build — read [Behaviour changes](#behaviour-changes) before
upgrading.

Conformance suite **142 → 153 cases**.

---

## Behaviour changes

### 1. A member filter's clauses must hold on ONE member row

This is the one to read.

`RefsetMembersFiltered` takes a single `MemberFilterOpts`, so several `{{ M … }}`
clauses were composed by calling it once per clause and intersecting the concept
sets. That is not what the expression asks. A reference set may hold **several rows
for the same member** — a complex map has one per map group — and intersecting per
clause accepts a concept whose *first* row satisfies one clause and whose *second*
satisfies another.

The specification's own examples are exactly this shape:

```
^ 447562003 |ICD-10 complex map| {{ M mapGroup = #2, mapPriority = #1, mapTarget = "J45.9" }}
```

The three clauses are there to pick **one** row. Answered per clause it returns
every concept that has a row in group 2, *and* a row at priority 1, *and* a row
mapping to J45.9 — a wider set, and silently so. Two of the 121 official ECL
examples have this shape.

| expression | before | after |
|---|---|---|
| `{{ M mapGroup = "2", mapTarget = "I10" }}` where a member has those in *different* rows | the member | nothing — or `ErrUnsupportedFeature` without the capability |
| `{{ M mapTarget = "G30.9" }}` — a single clause | unchanged | unchanged |

Several clauses now go to the new `ecl.RefsetFieldProjector`, which takes them all
on one call. Without that capability the multi-clause form is **reported** rather
than approximated. A single clause is unaffected and still uses
`RefsetMembersFiltered`, so the common case needs nothing.

### 2. `^ [*] X` no longer evaluates as `^ X`

The wildcard projection asks for every member field. It left no trace in the AST at
all, so it was indistinguishable from a plain `^` and quietly answered the default
projection — a narrower question than the one asked, with no indication that the
question had changed. It now returns `ErrUnsupportedFeature`: every field is a
table, and a `Set` is one column of concept ids.

`ast.MemberOf` gains an `AllFields` field. Additive; the existing `Fields` slice is
unchanged.

## New

### `ecl.DescriptionIDProvider` — `{{ D id = … }}`

The description id filter was the last filter the parser modelled and the evaluator
refused. It constrains a description's own SCTID:

```
<< 138875005 {{ D id = 751000000102 }}
```

A capability rather than a `DescriptionFilterOpts` field, for the reason every
other one exists: a new field is silently ignored by every provider written against
the current contract, so the id constraint would simply vanish and the filter would
return every concept satisfying the **other** clauses. That is not a smaller answer
but a wider one — and it is precisely what this filter used to do before it was
rejected outright.

The constraint is **per description row**, like negation:

| expression | result |
|---|---|
| `{{ D id = X, language = es }}` where X is the id of the Spanish description | the concept |
| `{{ D id = X, language = en }}` | nothing |

The concept has an English description *and* has that id — just not on the same
row.

Combining a description id filter with a **negated sibling clause** stays
unsupported: both negations are per row, one call cannot carry both, and guessing
which applies would answer a question nobody asked.

### `ecl.RefsetFieldProjector` — `^ [field] X`

`^ [targetComponentId] 900000000000527005 |SAME AS association reference set|` is
one of the specification's published examples, and this library rejected it.

The projection answers a **different question** from listing the members. The
members of an association reference set are the *inactive* concepts; the field
points at what replaced them:

| expression | result |
|---|---|
| `^ [referencedComponentId] 900000000000527005` | the inactive concept |
| `^ [targetComponentId] 900000000000527005` | what replaced it |

The old note said `Set` carries concept ids only, so a projection could never work.
That is true of `^[a,b]` and `^[*]`, which are tabular, and **false** of a single
component-id field — which is what the official example uses. Both tabular forms
are still reported, now saying why rather than implying the whole feature is
impossible.

A `{{ M … }}` filter travels **with** the projection rather than being applied to
the result: `^ [targetComponentId] X {{ M referencedComponentId = Y }}` filters one
column and returns another, so filtering the returned values would compare the
wrong column and return nothing.

A provider refusing a **field** wraps `ErrUnsupportedFeature`, and the evaluator
passes it through **without** adding `ErrProvider`. Only the provider knows which
member fields hold a component id, so the refusal has to come from there — but it
is a capability limit, not an unhealthy backend, and a caller mapping sentinels to
HTTP answers should say 501, not 503.

### Seven optional capabilities

| Interface | What it unlocks |
|---|---|
| `BatchPropertiesProvider` | One query per refinement instead of one per focus concept |
| `BatchConcreteValuesProvider` | The same for concrete-value comparisons |
| `InboundRelationshipsProvider` | `[m..n] R attr = value` and `R attr != value` |
| `NegatingDescriptionProvider` | `{{ D term != … }}`, `{{ D language != … }}`, `{{ D type != … }}` |
| `DialectAliasResolver` | `{{ D dialect = en-gb }}`, the alias form |
| **`DescriptionIDProvider`** | `{{ D id = … }}` |
| **`RefsetFieldProjector`** | `^ [field] X`, and a member filter with several clauses |

The reference provider in `ecl/providertest/fixture.go` implements all seven, and
`VerifyContract` has a check per capability.

## Testing

Every entry point that takes untrusted input now has a fuzz target: both parsers
and the MRCM loader. `ecl.Parse` was the one that was actually broken; the other
two were clean when measured, at 26.5M and 7.6M executions. The MRCM target fuzzes
the model **and** the expression, and runs the validator on every model the loader
accepts — a model that parses but then breaks `Validate` is the worse bug, because
it surfaces far from its cause. CI fuzzes all three on every pull request.

The differential oracle grew from 29 to 39 cases and now covers **reference sets
and history supplements**, the last two semantic families whose only judge was this
project. 35 agree against SNOMED CT on a live server, none of them vacuously. Three
skips are a defect in that server rather than in either implementation, named in
the README.

The MRCM in-group cardinality reading shipped in v1.4.0 as a decision under an
ambiguity. It is now **verified**: SNOMED International's Snowstorm renders each
MRCM row as `[0..*] { [0..1] attr = … }`, and under ECL a group cardinality of
`0..*` means a concept with no such group satisfies the rule — so an in-group
minimum never demands the attribute in a group that does not use it, which is what
this library enforces.

## Upgrading

1. `go get -u github.com/gofhir/ecl` — it compiles; no signature changed.
2. If you use `{{ M … }}` with **more than one clause**, you now need a provider
   implementing `ecl.RefsetFieldProjector`, or those expressions report
   `ErrUnsupportedFeature`. They were previously answered with a wider set than
   asked for, so results will also move where they still work.
3. If you use `^ [*]`, it now errors. Name a single field instead.
4. Snapshot tests over ECL results may move for both reasons above.
